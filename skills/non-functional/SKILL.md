# 非機能要件

性能・可用性・セキュリティ・運用・拡張性を決める。

**後から足すと設計をやり直すことになる。**
「1000万件でも動くか」「落ちてよいか」はテーブル設計とインフラ構成を左右する。

**共通規約 `${CLAUDE_PLUGIN_ROOT}/references/conventions.md` を必ず先に読むこと。**

## 開始前に必ず読むもの

```bash
cat docs/mitorizu/.feedback/overrides.md 2>/dev/null
cat docs/mitorizu/.feedback/learnings.md 2>/dev/null
```

## 前提

`requirements.md` があること。機能要件が決まっていないと規模が見積もれない。

## 成果物

```
docs/mitorizu/
  non-functional.md    # プロジェクト全体の非機能要件
```

**機能ごとではなくプロジェクト全体で1つ。**
性能や可用性は機能をまたいで決まるため。

## MVP での原則

**過剰な要件を設定しない。** 数値を大きくすると設計コストが跳ね上がる。

| よくある過剰 | MVP での現実 |
| --- | --- |
| 99.99% の可用性 | 99% (月7時間の停止を許容) で十分なことが多い |
| 1秒以内の応答 | 3秒でも業務は回る |
| 100万ユーザー | まず100人。10倍になってから考える |
| リアルタイム同期 | 数分の遅延を許容できることが多い |

**「将来必要かもしれない」で決めない。**
今の10倍までを想定し、それ以上は「その時に考える」と明記する。

ただし**後から変えるのが高コストなものは最初に決める**。

| 項目 | 後付けの難易度 | MVP での扱い |
| --- | --- | --- |
| データの暗号化 | **高** (既存データの移行が必要) | 最初に決める |
| 監査ログ | **高** (過去分が残らない) | 要否だけ決める |
| マルチテナント | **高** (全テーブルに影響) | 最初に決める |
| 個人情報の扱い | **高** (法的要件) | 最初に決める |
| 応答速度 | 低 (後から改善できる) | 目標だけ置く |
| 可用性 | 低 (構成変更で対応) | MVP は単一構成でよい |

## 進め方

### Phase 1: 規模を見積もる

**全ての非機能要件は規模から決まる。** まずここを確定させる。

AskUserQuestion で聞く。**分からなければ幅で答えてもらう。**

| 項目 | 聞き方 | 影響する設計 |
| --- | --- | --- |
| 利用者数 | 何人が使いますか (現在 / 1年後) | 認証、セッション、DB接続数 |
| データ量 | 主要なレコードは何件になりますか | インデックス、ページネーション |
| 同時アクセス | ピーク時に何人が同時に使いますか | サーバー台数、コネクションプール |
| 利用時間帯 | いつ使われますか | メンテナンス時間、スケーリング |

```
想定規模を教えてください。正確でなくて構いません。桁が分かれば十分です。

Q1. 利用者数は?
    A: 〜100人 (社内ツール規模)
    B: 〜1,000人
    C: 〜10,000人
    D: それ以上

Q2. 主要なデータ (注文・投稿など) は1年でどれくらい増えますか?
    A: 〜1万件
    B: 〜10万件
    C: 〜100万件
    D: それ以上
```

**桁が違えば設計が変わる。** 1万件と100万件では、必要なインデックスが違う。

### Phase 2: 性能要件を決める

**数値で書く。** 「速い」「快適」は要件にならない。

| 項目 | 書き方 | MVP の目安 |
| --- | --- | --- |
| 応答時間 | 一覧取得を95パーセンタイルで N ms 以内 | 1000ms |
| スループット | 秒間 N リクエスト | 10 rps |
| 同時接続 | N 接続まで | 50 |
| バッチ処理 | N 件を M 分以内 | - |

**測定条件も書く。** 「何件のデータで」「どの環境で」が無いと検証できない。

```markdown
[確実] NFR-001: システムは書籍一覧 API を、
       蔵書1,000件・同時10接続の条件下で、
       95パーセンタイル1,000ms 以内に応答すること。
```

### Phase 3: 可用性を決める

| 項目 | 問い | MVP の目安 |
| --- | --- | --- |
| 稼働率 | 月に何時間落ちてよいか | 99% (月7時間) |
| 復旧時間 (RTO) | 障害から何分で復旧すべきか | 4時間 |
| データ損失 (RPO) | 何分前までのデータを守るか | 24時間 (日次バックアップ) |
| メンテナンス | 計画停止は許容されるか | 許容する |

**MVP では単一構成でよいことが多い。**
Multi-AZ はコストが倍になる。要件が出てから対応する。

ただし**バックアップだけは最初から取る。** データを失うと復旧できない。

### Phase 4: セキュリティを決める

**後から変えられないものを優先する。**

| 項目 | 決めること | 後付けの難易度 |
| --- | --- | --- |
| 認証方式 | パスワード / OAuth / SSO | 中 |
| 通信の暗号化 | TLS のバージョン | 低 |
| 保存時の暗号化 | どのカラムを暗号化するか | **高** |
| 個人情報 | 何を保持するか。保持期間 | **高** |
| 監査ログ | 何を記録するか | **高** |
| 権限管理 | ロールの粒度 | 中 |

#### 個人情報の扱い

**MVP でも必ず決める。** 法的要件に関わる。

```markdown
| 情報 | 保持するか | 保持期間 | 暗号化 | 根拠 |
| --- | --- | --- | --- | --- |
| 氏名 | する | 退会後1年 | しない | 業務上必要 |
| メールアドレス | する | 退会後1年 | しない | 認証に必要 |
| 電話番号 | **しない** | - | - | 業務上不要 |
| クレジットカード | **しない** | - | - | 決済代行に委ねる |
```

**保持しないという判断が最も安全。** 必要になってから追加する。

### Phase 5: 運用を決める

| 項目 | 決めること | MVP の目安 |
| --- | --- | --- |
| ログ | 何を記録するか。保持期間 | アプリログ30日 |
| 監視 | 何を監視するか。通知先 | 死活監視のみ |
| バックアップ | 頻度と保持期間 | 日次・7世代 |
| デプロイ | 頻度。ダウンタイムの許容 | 週次・許容する |
| 障害対応 | 誰が対応するか。連絡経路 | - |

**MVP では監視を最小にしてよい。** ただし**死活監視だけは入れる。**
落ちていることに気づかないのが最悪。

### Phase 6: 拡張性を決める

**今の10倍までを想定する。** それ以上は「その時に考える」と明記する。

| 項目 | 問い |
| --- | --- |
| データ量の増加 | 10倍になったとき何が壊れるか |
| 利用者の増加 | 10倍になったとき何が詰まるか |
| 機能の追加 | どこに拡張余地を残すか |

```markdown
[推測] NFR-020: 蔵書が10,000件 (現在の10倍) になった場合、
       一覧画面はページネーションで対応する。
       それ以上は検索機能の追加を検討する (現時点では設計しない)。
```

**「無限にスケールする設計」を目指さない。** MVP では過剰。

### Phase 7: 検証方法を書く

**どう確認するかを書かない要件は、満たされたか分からない。**

```markdown
| 要件ID | 検証方法 | 実施時期 |
| --- | --- | --- |
| NFR-001 | 蔵書1,000件を投入し、ab で10並列100リクエストを実行 | 実装後 |
| NFR-010 | 障害を意図的に起こし、復旧手順書に従って復旧できるか確認 | リリース前 |
| NFR-020 | (検証しない。設計上の想定のみ) | - |
```

**検証しないものは「検証しない」と書く。** 曖昧にしない。

### Phase 8: 記録と次のステップ

1. `[要確認]` を一覧で再掲する
2. `docs/mitorizu/README.md` に非機能要件の節を追加する
3. **後から変えられない決定は ADR に記録するよう案内する**

```
次のステップ:
- /mitorizu:adr           後から変えられない決定を記録する
- /mitorizu:data-model    ここで決めた規模を前提にテーブルを設計する
- /mitorizu:infra-diagram ここで決めた可用性を前提に構成を描く
```

### 終了前: 学んだことを記録する

利用者から訂正を受けたら、次回も同じ判断をすべきものだけを
`docs/mitorizu/.feedback/overrides.md` に追記する。**確認してから書く。**

## 書き方の原則

### 1. 数値で書く

```
悪い: システムは高速に応答すること
良い: システムは一覧 API を95パーセンタイル1,000ms 以内で応答すること
```

### 2. 測定条件を添える

```
悪い: 1,000ms 以内に応答する
良い: 蔵書1,000件・同時10接続の条件下で1,000ms 以内に応答する
```

条件が無いと、何をもって達成とするか決まらない。

### 3. 分からないものは [要確認] にする

推測で数値を置いてよい。ただし**マーカーを付けて、根拠を書く**。

```markdown
[要確認] NFR-005: 同時接続数は50を上限とする
  仮置きの根拠: 利用者100人の半数が同時に使うと想定
  確認事項: 実際の利用パターン (朝礼後に集中するなど)
```

### 4. MVP で決めないことも書く

```markdown
## MVP では決めないこと

| 項目 | 理由 | いつ決めるか |
| --- | --- | --- |
| 多言語対応 | 国内利用のみ | 海外展開を検討する時 |
| SLA | 社内ツールのため契約なし | 外部提供する時 |
```
