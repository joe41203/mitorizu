# 設計ドキュメントの目次

`docs/mitorizu/README.md` を生成・更新する。

**これは単なる目次ではない。**
各成果物の要約を含み、**この1枚を読めば全体像が分かる**文書にする。
詳細を知りたくなったときに各ファイルへ飛べる、という構造。

**共通規約 `${CLAUDE_PLUGIN_ROOT}/references/conventions.md` を必ず先に読むこと。**

## いつ使うか

| 状況 | 動作 |
| --- | --- |
| 初回 (README.md が無い) | 既存の成果物を全て読んで新規作成する |
| 成果物が増えた | 該当する節を更新する |
| 全体を作り直したい | 全成果物を読み直して再生成する |

各スキル (requirements / screens / data-model / api-design / infra-diagram) は
最終フェーズで README の該当節を自動更新する。
このスキルは**全体を作り直す / 初回に作る**ときに使う。

## 成果物

```
docs/mitorizu/README.md
```

## 進め方

### Phase 1: 既存の成果物を収集する

```bash
find docs/mitorizu -name '*.md' -o -name '*.yaml' -o -name '*.d2' | sort
```

読み込む対象:

| ファイル | 抽出する情報 |
| --- | --- |
| `features/*/requirements.md` | 機能名、目的、要件数、`[要確認]` |
| `features/*/screens.md` | 画面一覧、画面数 |
| `features/*/data-model.md` | エンティティ名、テーブル数 |
| `features/*/api.md` | エンドポイント一覧 |
| `features/*/traceability.md` | 検証結果 (不足・過剰の件数) |
| `glossary.md` | 用語数 |
| `entities.md` | エンティティ一覧 |
| `decisions.md` | 主要な決定 |
| `adr/*.md` | ADR のタイトルと状態 |
| `infra/*.d2` | インフラ構成の有無 |

**ファイル数が多い場合は Explore サブエージェントに委譲**し、
メインコンテキストを温存する。抽出した要約だけを受け取る。

### Phase 2: README を生成する

`${CLAUDE_SKILL_DIR}/references/docs-readme-template.md` の構造に従う。

**要約の書き方が重要。**

| 節 | 書くこと | 書かないこと |
| --- | --- | --- |
| サービス概要 | 何を解決するか、誰が使うか | 実装の詳細 |
| 機能一覧 | 各機能1〜3行の要約 + リンク | 要件の全文 |
| データモデル | エンティティの関係を1段落 + ER図 | 全カラムの定義 |
| API | エンドポイント一覧の表 | レスポンスの全フィールド |
| インフラ | 構成図 + 意図を数行 | 個々のリソース設定 |

**各節は「詳細は別ファイル」で終わらせない。**
要約だけでも意味が通る分量を書く。ただし全文をコピーしない。

### Phase 3: 横断情報を集約する

README にしかない情報を作る。個々の成果物には無い、全体を俯瞰する情報。

#### 進捗状況

機能ごとに、どのフェーズまで完了しているかを表にする。

```markdown
| 機能 | 要件 | 画面 | データ | API | 状態 |
| --- | --- | --- | --- | --- | --- |
| 注文管理 | 完了 | 完了 | 完了 | 完了 | 設計完了 |
| 在庫管理 | 完了 | 完了 | - | - | 設計中 |
| 通知 | - | - | - | - | 未着手 (MVP対象外) |
```

**未着手・MVP対象外も書く。** 何をやらないかが分かることに価値がある。

#### 要確認項目の集約

全機能の `[要確認]` を1箇所に集める。**これが確認作業のチェックリストになる。**

```markdown
| 機能 | 項目 | 内容 | 仮置き |
| --- | --- | --- | --- |
| 注文管理 | REQ-003 | セッションタイムアウト | 30分 |
| 在庫管理 | REQ-021 | 在庫の引当タイミング | 注文確定時 |
```

件数が0なら「なし」と明記する。空欄にしない。

#### 検証結果

`traceability.md` の結果を集約する。

```markdown
| 機能 | 不足 | 過剰 | 出所不明 | 判定 |
| --- | --- | --- | --- | --- |
| 注文管理 | 0 | 0 | 0 | OK |
| 在庫管理 | 2 | 1 | 0 | **要対応** |
```

**0件でない機能があれば、README の冒頭で警告する。**

### Phase 4: 図を埋め込む

README には図を直接埋め込む。リンクだけにしない。

- **データフロー図・ER図** — mermaid をそのまま埋め込む (GitHub で描画される)
- **インフラ構成図** — `![](./infra/production.svg)` で画像参照 (D2 は描画されない)

複数機能がある場合、ER図は**全機能を統合した1枚**を README に置く。
機能ごとの詳細は各 `data-model.md` にある。

mermaid を書いたら検証する。

```bash
"${CLAUDE_PLUGIN_ROOT}/scripts/check-mermaid.sh" docs/mitorizu/README.md
```

### Phase 5: 更新モードの場合

README が既に存在する場合、**該当する節だけを更新する。**

1. 既存の README を読む
2. 更新対象の節を特定する
3. その節のみを書き換える
4. 「最終更新」の日付を更新する

**他の節に触れない。** 手で加筆された内容を消してしまう。

節の見出しは固定する (テンプレートの構造を維持する)。
見出しが変わると、次回の更新で該当節を見つけられなくなる。

## 分量の目安

| 項目 | 目安 |
| --- | --- |
| 全体 | 200〜500行 |
| サービス概要 | 10〜20行 |
| 機能ごとの要約 | 5〜15行 |
| 各節の要約 | 段落1〜3つ |

**500行を超えたら、機能数が多すぎるか要約が冗長。**
機能ごとの要約を削り、詳細は各ファイルに任せる。

逆に**100行未満なら要約が足りない。**
「詳細は別ファイル」で終わらせず、読んで意味が通る分量を書く。
