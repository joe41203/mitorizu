# ステークホルダー分析

**関係者を洗い出し、それぞれが何を気にするかを整理する。**

システムを使う人だけを見ると、後から差し戻される。
使わないが影響を受ける人の要求を、最初に拾う。

**共通規約 `${CLAUDE_PLUGIN_ROOT}/references/conventions.md` を必ず先に読むこと。**
特に第4節の「読み手と用語の使い分け」に従う (この文書は技術用語を使わない)。

## 開始前に必ず読むもの

```bash
cat docs/mitorizu/.feedback/overrides.md 2>/dev/null
cat docs/mitorizu/.feedback/learnings.md 2>/dev/null
```

## 位置づけ

```
discovery      課題と機能候補
features       機能の分割
stakeholders   関係者と関心事          <- ここ
business-flow  業務の流れ
requirements   システム要件
```

**business-flow の前に実行する。**
登場人物が確定していないと業務フローが描けない。

## 成果物

```
docs/mitorizu/
  stakeholders.md    # 関係者と関心事 (プロジェクト全体で1つ)
```

**機能ごとではなくプロジェクト全体で1つ。**
関係者は機能をまたいで存在する。

## 進め方

### Phase 1: 3つの層で洗い出す

**使う人だけを見ない。** 以下の3層で考える。

| 層 | 説明 | 見落としやすい例 |
| --- | --- | --- |
| **使う人** | 日常的にシステムを操作する | - |
| **影響を受ける人** | 使わないが業務が変わる | 経理、上長、取引先 |
| **決める人・止める人** | 承認・予算・規制 | 決裁者、法務、情報システム部門、監査 |

**3層目が最も見落とされる。** そして最も後から効いてくる。

```
「セキュリティ要件を情報システム部門に確認したら、
 社外からのアクセスは VPN 必須と言われた」
-> 設計をやり直すことになる
```

### Phase 2: 関係者ごとの関心事を書く

**「この人は何を気にするか」を書く。** 要求ではなく関心事。
関心事から要求が導かれる。

```markdown
| 関係者 | 立場 | 関心事 | 想定される要求 | 影響度 |
| --- | --- | --- | --- | --- |
| 社員 | 使う人 | 手間なく借りたい | 3クリック以内で貸出できる | 高 |
| 管理者 | 使う人 | 蔵書の所在を把握したい | 一覧で貸出状況が分かる | 高 |
| 経理 | 影響を受ける | 資産管理との整合 | 蔵書の取得価額を記録できる | 中 |
| 情報システム部門 | 決める人 | 社内システムの標準に沿うか | SSO 連携、ログの保全 | **高** |
| 総務部長 | 決める人 | 予算と効果 | 導入コストの説明 | 中 |
```

**影響度は「この人の要求を無視したらどうなるか」で決める。**

| 影響度 | 意味 |
| --- | --- |
| 高 | 無視すると導入できない、または作り直しになる |
| 中 | 無視すると後から機能追加が必要になる |
| 低 | 無視しても大きな問題にならない |

### Phase 3: 決める人・止める人を特定する (最重要)

**誰の承認が必要かを明確にする。**

| 種類 | 誰か | 何を承認するか | いつ確認するか |
| --- | --- | --- | --- |
| 予算 | 総務部長 | 導入費用 | 着手前 |
| セキュリティ | 情報システム部門 | 認証方式、データの保存先 | **設計前** |
| 個人情報 | 法務 | 収集する情報の範囲 | **設計前** |
| 業務ルール | 現場のリーダー | 貸出期間、上限冊数 | 要件定義時 |

**「設計前」の確認を後回しにしない。**
セキュリティと個人情報の要求は、後から満たすのが最も高コスト。

### Phase 4: 対立する要求を見つける

**関係者の要求は必ず対立する。** 先に見つけて調整する。

```markdown
| 対立 | 一方の要求 | 他方の要求 | 調整案 |
| --- | --- | --- | --- |
| 利便性 vs セキュリティ | 社員: パスワード入力を減らしたい | 情シス: 認証を厳格にしたい | 社内ネットワークからは SSO、社外は多要素認証 |
| 記録 vs プライバシー | 管理者: 誰が何を借りたか知りたい | 社員: 読書履歴を見られたくない | 貸出中のみ表示、返却後は管理者のみ閲覧可 |
```

**調整案が出せない対立は、決裁者に判断を仰ぐ。**
設計側で勝手に決めない。

### Phase 5: 確認の計画を立てる

**誰にいつ確認するかを決める。** 確認しないまま進めない。

```markdown
| # | 確認する相手 | 確認すること | 期限 | 状態 |
| --- | --- | --- | --- | --- |
| 1 | 情報システム部門 | 認証方式、データの保存先 | 設計前 | **未確認** |
| 2 | 法務 | 個人情報の範囲と保持期間 | 設計前 | **未確認** |
| 3 | 現場リーダー | 貸出期間と上限冊数 | 要件定義時 | 確認済 (14日/5冊) |
```

**未確認のまま設計を進める場合、`[要確認]` として明示する。**
後から覆る前提の上に設計を積むと、手戻りが大きい。

### Phase 6: 記録と次のステップ

1. `[要確認]` を一覧で再掲する
2. `docs/mitorizu/README.md` に関係者の節を追加する
3. **影響度「高」で未確認の関係者がいれば警告する**

```
ステークホルダーを整理しました。

  docs/mitorizu/stakeholders.md

**確認が必要です:**
  情報システム部門 (影響度: 高) — 認証方式が未確認です。
  これが決まらないと requirements で認証要件を書けません。

次のステップ:
- /mitorizu:business-flow  業務の流れを描く
```

### 終了前: 学んだことを記録する

利用者から訂正を受けたら、次回も同じ判断をすべきものだけを
`docs/mitorizu/.feedback/overrides.md` に追記する。**確認してから書く。**

## 個人開発・社内ツールの場合

**関係者が自分だけなら、このスキルは簡略化してよい。**

ただし以下は確認する。

| 項目 | 個人開発でも確認する理由 |
| --- | --- |
| 実際に使う人がいるか | 自分しか使わないなら要件が変わる |
| 会社の規約に触れるか | 社内ツールでも情報システム部門の規約はある |
| 個人情報を扱うか | 扱うなら法的要件がある |

```
関係者はあなた1人ですか?
それとも他に使う人、影響を受ける人がいますか?

A: 自分だけ (このスキルを簡略化します)
B: 他にもいる (詳しく洗い出します)
```

Aなら3行程度の記録で終える。過剰な分析はしない。

## よくある失敗

### 1. 使う人だけを見る

最も多い失敗。情報システム部門の要求を後から知り、設計をやり直すことになる。

### 2. 「決める人」を後回しにする

予算とセキュリティの承認は最初に取る。
作ってから「予算が下りない」「セキュリティ要件を満たさない」となるのが最悪。

### 3. 対立を見て見ぬふりをする

利便性とセキュリティは必ず対立する。
先に調整案を出さないと、実装後に揉める。

### 4. 過剰に分析する

個人開発で関係者が自分だけなら、詳細な分析は不要。
**規模に合わせる。**
