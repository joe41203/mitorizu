# 調査サブエージェントへの指示テンプレート

`discovery` スキルが並列で投げる調査の指示文。

**単一メッセージ内で複数の Task 呼び出しを並べる。** 逐次実行にしない。

## 全調査に共通して入れる指示

```
## 調査の作法 (必ず守ること)

- 推測で断定しない。WebSearch / WebFetch で必ず裏を取る
- 出典 URL を必ず添える
- 数値 (star数、価格、ユーザー数、市場規模) は取得元と取得日を明記する
- 「見つからなかった」ことも報告する。該当なしは有用な情報
- 他の調査軸には踏み込まない (別のエージェントが担当している)
- 絵文字は使わない
- 日本語で報告する

## 注意

あなたの記憶は古い可能性がある。サービスの現状 (終了していないか、
価格が変わっていないか、最終更新はいつか) は必ず実際に確認すること。
```

---

## 軸1: 競合・既存サービス

```
「<アイデアの1行説明>」という課題を解決する既存のサービス・プロダクトを調査してください。

## 調査対象

- 商用 SaaS
- OSS (GitHub で star が付いているもの)
- 大手サービスの一機能として提供されているもの
- 国内・海外の両方

## 各サービスについて整理すること

1. 名前と URL
2. 何をするツールか (入力 -> 出力)
3. 主要な機能の一覧
4. 価格 (無料枠の有無、有償プランの金額)
5. 規模の指標 (star数 / 導入企業数 / ユーザー数。分かる範囲で。取得日を明記)
6. 活発さ (OSS なら最終コミット、商用なら最終アップデート)
7. 弱点・不満として語られていること

## 出力形式

まず一覧表 (名前 / 種別 / 価格 / 規模 / 最終更新)。
次に、上位3〜5件について詳細。
最後に「この領域は既に埋まっているか、まだ空きがあるか」の見立て。

## 特に知りたいこと

同じ課題を解くツールが既に十分あるなら、率直にそう報告してください。
「作らないほうがよい」という結論も有用です。
```

---

## 軸2: 利用者の声 (不満・要望)

```
「<課題の1行説明>」について、実際の利用者が何に困っているかを調査してください。

## 探す場所

- 既存サービスのレビュー (G2, Capterra, App Store, Google Play)
- GitHub の Issues (OSS の場合。特に長期間 open なもの)
- Reddit / Hacker News / Stack Overflow
- 日本語圏: Qiita, Zenn, note, X (Twitter), はてなブックマーク
- 業界のフォーラム・コミュニティ

## 収集すること

1. 具体的な不満 (「〜が使いにくい」「〜ができない」)
2. 要望 (「〜が欲しい」)
3. 回避策 (「〜で代用している」)
4. 諦めの声 (「結局 Excel に戻した」)

## 出力形式

| 声 | 出典 | 日付 | 頻度 |
| --- | --- | --- | --- |
| <実際の文言を引用> | <URL> | <投稿日> | <同種の声を何件見たか> |

**複数の情報源で繰り返し出てくる不満** を最後にまとめてください。
1件だけの声と、10件ある声は重みが違います。

## 注意

- 引用は実際の文言を使う。要約しすぎない
- ステマ・宣伝目的の投稿は除外する
- 古い投稿 (2年以上前) は現在も該当するか注記する
```

## 軸3: 代替手段 (今どうしているか)

```
「<課題の1行説明>」を、今の人々がどうやって解決しているかを調査してください。

専用ツールを使っていない場合の方法に注目してください。

## 調べること

1. **手作業での方法** — Excel, スプレッドシート, 紙, ホワイトボード
2. **既存ツールの流用** — Slack, Notion, Trello, Google Forms などの応用
3. **自作スクリプト** — GAS, Zapier, 社内ツール
4. **そもそも解決していない** — 諦めている / 問題と認識していない

## 各手段について

| 手段 | どう使っているか | 限界・不満 | 出典 |
| --- | --- | --- | --- |

## 特に知りたいこと

- **なぜ専用ツールを導入しないのか** (コスト? 手間? 知らない?)
- **その方法で十分に回っているのか** (回っているなら課題は小さい)
- **乗り換えの障壁は何か** (データ移行? 学習コスト? 承認?)

代替手段で十分に解決されているなら、率直にそう報告してください。
```

## 軸4: 市場とビジネス

```
「<アイデアの1行説明>」の市場性と収益モデルを調査してください。

## 調べること

1. **市場規模**
   - 対象となる企業数・個人数 (国内 / 海外)
   - 市場規模の推計値があれば (出典と調査年を明記)
   - 成長しているか縮小しているか

2. **収益モデル**
   - 類似サービスの課金方式 (月額 / 従量 / 買い切り / フリーミアム)
   - 価格帯 (最安 / 中央値 / 最高)
   - 無料枠の設定

3. **成否の事例**
   - 成功しているサービスとその要因
   - 終了・撤退したサービスとその理由 (これが最も有用)

4. **参入障壁**
   - 法規制・認証の要否
   - 既存プレイヤーのロックイン
   - ネットワーク効果の有無

## 出力形式

数値は必ず出典と調査年を添えてください。
「<出典>によると2025年時点でN社」のように書き、
推計値と実測値を区別してください。

## 注意

市場規模の数値はマーケティング資料で誇張されがちです。
一次情報 (政府統計、業界団体の調査) を優先してください。
```

## 第2段階: 深掘りの指示

第1段階の結果から3〜5件を選んで深掘りする。

```
<対象> について詳しく調査してください。第1段階で以下が分かっています。

<第1段階の該当部分を貼る>

## 深掘りすること

1. 機能の詳細 (実際の画面や仕様書を確認する)
2. 価格の内訳 (プラン別に何が使えるか)
3. 利用者の評価 (良い点と悪い点を具体的に)
4. 技術的な構成 (公開されていれば)
5. **弱点** — 何ができないか、何が不満とされているか

## 特に知りたいこと

私たちが作ろうとしているものと比べて、
- どこが優れているか
- どこに隙があるか
- 乗り換えてもらうには何が必要か

## 出力

事実と解釈を分けて書いてください。
「公式ドキュメントに X と書かれている」(事実) と
「そのため Y が弱いと思われる」(解釈) を混ぜないこと。
```

## 結果を受け取った後の作法

### 信じすぎない

サブエージェントの報告にも誤りが混ざる。以下は特に注意する。

| 注意点 | 対処 |
| --- | --- |
| star 数・価格が古い | 取得日を確認。1年以上前なら再確認 |
| 「最新」の判断が誤り | リリース日・最終コミットを確認 |
| 存在しないサービスを報告 | URL を実際に開く |
| 検索結果の要約が原文と違う | 判断を左右する数値は原典を当たる |
| 終了したサービスを現役として報告 | 公式サイトの更新日・お知らせを確認 |

**判断を左右する数値は、メイン側でも1つは裏を取る。**

### 重複を除く

4軸は独立して調査するため、同じサービスが複数の報告に出てくる。
`competitors.md` に統合する際、情報を突き合わせて矛盾があれば再確認する。

### 出典を集約する

全ての URL を `sources.md` に集める。後から検証できる状態を保つ。

```markdown
| # | URL | 何の根拠か | 取得日 |
| --- | --- | --- | --- |
| S-01 | https://... | 競合Aの価格 | 2026-08-14 |
```

本文からは `[S-01]` のように参照する。
