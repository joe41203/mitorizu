# 課題発見と機能の洗い出し

ざっくりしたアイデアから、**何を作るべきか** を Web 調査で洗い出す。

**このスキルは要件定義の前段。** 作るものが既に決まっているなら不要で、
`/mitorizu:requirements` から始めてよい。

**共通規約 `${CLAUDE_PLUGIN_ROOT}/references/conventions.md` を必ず先に読むこと。**

## このスキルが答える問い

| 問い | 出力 |
| --- | --- |
| 誰のどんな課題を解くのか | 課題の仮説と根拠 |
| 既に誰かが解いていないか | 競合・既存サービスの一覧と機能比較 |
| 利用者は何に困っているのか | 実際の不満・要望の収集結果 |
| 何を作れば価値が出るのか | 機能候補と優先度 |
| MVP には何を入れるのか | 最小構成の提案と、あえて外すもの |
| 儲かるのか / 続けられるのか | 市場規模と収益モデルの見立て |

## 開始前に必ず読むもの

**成果物を書き始める前に、このプロジェクトの学習内容を読む。**
既定より優先度が高い。

```bash
cat docs/mitorizu/.feedback/overrides.md 2>/dev/null
cat docs/mitorizu/.feedback/learnings.md 2>/dev/null
```

無ければ既定で進める。あれば**そちらを優先する**。
詳細は共通規約の「フィードバックの蓄積と反映」を参照。

## 成果物

```
docs/mitorizu/discovery/
  README.md            # 調査結果のまとめ (これを読めば判断できる)
  problem.md           # 課題の定義と根拠
  competitors.md       # 競合・既存サービスの調査
  voices.md            # 利用者の声 (不満・要望)
  features.md          # 機能候補と優先度
  business.md          # 市場・収益モデル
  sources.md           # 参照した URL の一覧
```

## 進め方

### Phase 0: アイデアを言語化する

まず**何を作りたいのか**を1〜2文で言語化させる。曖昧なままでは調査軸が決まらない。

以下が埋まらなければ、AskUserQuestion で1問ずつ聞く。

| 項目 | 例 |
| --- | --- |
| 誰が使うか | 社内の開発者 / 個人の副業ワーカー / 小規模飲食店の店主 |
| 何をしたいか | 蔵書を借りる / 経費を記録する / 予約を受ける |
| なぜ今の方法では困るか | Excel で管理していて誰が持っているか分からない |

**「なぜ困るか」が最も重要。** ここが空欄なら、解くべき課題が存在しない可能性がある。
その場合は率直に伝える。

### Phase 1: 並列で広く調査する (第1段階)

**4つの軸を別々のサブエージェントに並列で投げる。**
メインコンテキストを汚さず、結果の要約だけを受け取る。

Task tool を単一メッセージ内で4つ並べて呼び出す。

| # | 調査軸 | 何を調べるか |
| --- | --- | --- |
| 1 | **競合・既存サービス** | 同じ課題を解くサービス。商用・OSS 両方。機能・価格・規模 |
| 2 | **利用者の声** | 実際の不満・要望。レビュー、フォーラム、SNS、Q&A サイト |
| 3 | **代替手段** | 今どうやって解決しているか。Excel、紙、既存ツールの流用 |
| 4 | **市場とビジネス** | 市場規模、収益モデル、類似サービスの価格帯と成否 |

各サブエージェントへの指示に必ず含めること:

```
- 推測で断定しないこと。WebSearch / WebFetch で必ず裏を取る
- 出典 URL を必ず添える
- 数値 (star数、価格、ユーザー数) は取得元と取得日を明記する
- 見つからなかったことも報告する (「該当なし」は有用な情報)
- 絵文字は使わない
```

**「見つからなかった」は失敗ではない。**
競合が存在しないなら、市場が無いか、まだ誰も気づいていないかのどちらか。
どちらであるかを判断する材料になる。

### Phase 2: 深掘りする (第2段階)

第1段階の結果を読み、**重要そうなものだけ**を深掘りする。全部は掘らない。

深掘りの対象を選ぶ基準:

| 基準 | 例 |
| --- | --- |
| 最も近い競合 | 機能・価格・弱点を詳細に |
| 繰り返し出てくる不満 | 複数の情報源で言及されるもの |
| 想定と食い違った点 | 「無いと思っていたが既にあった」など |
| 判断を左右する数値 | 市場規模、価格帯、乗り換えコスト |

**3〜5件に絞る。** 深掘りもサブエージェントに委譲する。

第1段階の結果をユーザーに提示し、深掘り対象を確認してもよい。
非対話なら上記の基準で自動選定する。

### Phase 3: 課題を定義する

調査結果から、**解くべき課題**を絞り込む。

`problem.md` に書く内容:

```markdown
## 課題

[確実] 社内の技術書が誰の手元にあるか分からず、探すのに時間がかかる
  根拠: (ヒアリング内容 / 調査で見つかった同種の不満)

## 誰の課題か

| 対象 | 課題の深刻さ | 根拠 |
| --- | --- | --- |
| 借りたい人 | 高 (欲しい本が見つからない) | ... |
| 管理者 | 中 (棚卸しができない) | ... |

## 既存の解決手段とその限界

| 手段 | 限界 | 出典 |
| --- | --- | --- |
| Excel 台帳 | 更新されない。誰も見ない | ... |
| Slack で聞く | 流れて消える。回答が来ないことがある | ... |

## 検証したい仮説

[要確認] 貸出状況が一覧で見えれば、探す時間が減る
  検証方法: MVP をリリースし、利用率と「探した」という声の減少を見る
```

**「課題が存在しない」という結論もありうる。**
調査の結果、既存手段で十分に解決されているなら、率直にそう書く。
作るべきでないものを作らせないことも、このスキルの役割。

### Phase 4: 機能を洗い出して優先度を付ける

`features.md` に、**機能候補を全て挙げてから削る**。

```markdown
## 機能候補

| # | 機能 | 解く課題 | 競合の実装 | 優先度 | MVP |
| --- | --- | --- | --- | --- | --- |
| F-01 | 蔵書の一覧表示 | 探せない | 全社が実装 | 必須 | 含む |
| F-02 | 貸出・返却 | 所在が不明 | 全社が実装 | 必須 | 含む |
| F-03 | 検索 | 探せない | 全社が実装 | 高 | **除外** |
| F-04 | 予約 | 貸出中で借りられない | 3社中2社 | 中 | 除外 |
| F-05 | 通知 | 返却を忘れる | 3社中3社 | 中 | 除外 |
| F-06 | 蔵書のレコメンド | (課題に紐づかない) | 0社 | 低 | 除外 |
```

**「解く課題」が空欄の機能は作らない。**
競合が実装していても、こちらの課題に紐づかないなら不要。

優先度の判断基準:

| 優先度 | 基準 |
| --- | --- |
| **必須** | これが無いと課題が解けない |
| **高** | 無くても成立するが、価値が大きく下がる |
| **中** | あると便利。無くても使える |
| **低** | 課題との紐づきが弱い |

MVP に入れるのは原則**必須のみ**。
「高」を入れるかは、実装コストと検証したい仮説次第で判断する。

### Phase 5: ビジネス面を整理する

`business.md` に、続けられるかの見立てを書く。

```markdown
## 市場規模

[推測] 国内の該当企業数: 約N社 (出典: ...)
[要確認] そのうち課題を認識している割合: 不明

## 収益モデルの候補

| モデル | 類似サービスの価格 | 適合度 | 備考 |
| --- | --- | --- | --- |
| 月額課金 | 1,000〜5,000円/月 | 高 | 競合3社中3社がこのモデル |
| 買い切り | - | 低 | 継続的な運用コストを回収できない |
| 無料 + 有償サポート | - | 中 | 社内利用なら課金不要 |

## 差別化の候補

| 軸 | 競合の状況 | 勝ち筋があるか |
| --- | --- | --- |
| 価格 | 3社とも月3,000円前後 | 弱い (価格競争は消耗する) |
| 導入の容易さ | 全社がアカウント登録必須 | **あり** (Slack 連携のみで完結) |

## 撤退・縮小の判断基準

[要確認] リリース後3ヶ月で週次利用者が10人に満たなければ縮小を検討する
```

**社内ツールなど収益を伴わない場合は、この Phase を省略してよい。**
その場合「収益モデルなし (社内利用)」と明記する。

### 終了前: 学んだことを記録する

このフェーズで**利用者から訂正や指示**を受けたら、
次回も同じ判断をすべきものだけを `docs/mitorizu/.feedback/overrides.md` に追記する。

**記録する前に利用者に確認する。**

```
以下を次回以降の既定にしますか?
  「テーブル名は単数形を使う」(今回のご指摘)

A: 記録する (次回から自動で適用)
B: 今回限り (記録しない)
```

その場限りの指示 (機能名、今回の値) は記録しない。

### Phase 6: まとめと次のステップ

`docs/mitorizu/discovery/README.md` に、**判断できる形で**まとめる。

```markdown
# 調査結果: <アイデア名>

## 結論

[確実] 課題は実在する。ただし既存サービスXが80%を解決済み。
       差別化は「Slack 完結」に絞るべき。

## MVP に入れる機能 (3件)

| 機能 | 理由 |
| --- | --- |
| 蔵書一覧 | 課題の中核 |
| 貸出・返却 | 課題の中核 |
| Slack 連携 | 唯一の差別化点 |

## あえて外すもの (5件)

| 機能 | 理由 | 後から追加する難易度 |
| --- | --- | --- |
| 検索 | 蔵書100冊なら一覧で足りる | 低 |
| 通知 | 返却遅延が問題化してから | 低 |

## 要確認 (3件)

- 蔵書数の想定 (100冊か1000冊かで設計が変わる)
- Slack 以外の連携が必要か
- 予算 (有償サービスで代替できる可能性がある)
```

次のステップを案内する。

```
次のステップ:
- /mitorizu:requirements  この調査結果をもとに要件を固める
```

`requirements` は `discovery/` があればそれを読み、
**調査済みのことを聞き直さない**。

## サブエージェント委譲の作法

### 並列で投げるとき

**単一メッセージ内で複数の Task 呼び出しを並べる。** 逐次実行にしない。

各サブエージェントには以下を必ず渡す。

1. **調査の目的** — 何のための調査か (判断の質が変わる)
2. **調べる対象** — 具体的な軸
3. **裏取りの指示** — 推測で断定しない、URL 必須
4. **出力形式** — 表形式、見出し構成
5. **やらないこと** — 他の軸には踏み込まない (重複を避ける)

### 結果を受け取るとき

- **要約だけをメインコンテキストに取り込む**
- 出典 URL は `sources.md` に集約する
- 数値は取得元と取得日を残す (陳腐化するため)

### 調査結果を信じすぎない

サブエージェントの報告にも誤りが混ざる。以下は特に注意する。

| 注意点 | 対処 |
| --- | --- |
| star 数やユーザー数が古い | 取得日を確認する |
| 「最新」の判断が誤っている | リリース日を確認する |
| 存在しないサービスを報告する | URL を実際に開いて確認する |
| 検索結果の要約が原文と違う | 重要な数値は原典を当たる |

**判断を左右する数値は、メイン側でも1つは裏を取る。**
