# 検証結果の報告形式

`/mitorizu:validate` の出力形式。

**このスキルは修正しない。報告だけを行う。**
何を直すかは利用者の判断であり、勝手に書き換えると意図しない変更が混ざる。

## 基本構造

```
検証結果: N件の問題を検出しました
対象: 機能M件 / ドキュメントK件

重大 (実装が止まる)
  1. [種別] 問題の要約
     ファイル:行 / 関連ファイル:行
     -> どう直せばよいか (1行)

軽微 (設計の質)
  2. [種別] ...

情報 (判断が必要)
  3. [種別] ...
```

## 重大度の分類

| 重大度 | 意味 | 該当する種別 |
| --- | --- | --- |
| **重大** | 実装が止まる。設計として成立していない | 不足、出所不明、要件の矛盾、エンティティ重複 |
| **軽微** | 実装はできるが設計の質が下がる | 過剰、用途の空欄、マーカー欠落、命名規約違反 |
| **情報** | 判断が必要だが誤りとは限らない | 用語のブレ、未使用カラム、要確認の残存 |

**重大が1件でもあれば「実装に進める状態ではない」と明示する。**

## 種別のラベル

| ラベル | 意味 |
| --- | --- |
| `[不足]` | 画面に表示するが API が返さない |
| `[過剰]` | API が返すがどの画面でも使わない |
| `[出所不明]` | API が返すがテーブルに裏付けが無い |
| `[用途空欄]` | カラムに用途か参照元が書かれていない |
| `[未使用]` | テーブルにあるがどの API でも返さない |
| `[用語]` | 同じ概念に別名が付いている |
| `[重複]` | 同じエンティティが複数機能で定義されている |
| `[矛盾]` | 両立しない要件がある |
| `[追跡漏れ]` | 要件に対応する画面や API が無い |
| `[マーカー]` | 信頼性マーカーが付いていない |
| `[EARS]` | 機能要件が EARS 記法になっていない |
| `[命名]` | Rails 規約 (または既存規約) に従っていない |
| `[図]` | mermaid や D2 に構文エラーがある |
| `[陳腐化]` | traceability.md が他のファイルより古い |

## 記述の原則

### 1. ファイルと行を必ず示す

```
悪い: screens.md に不整合があります
良い: screens.md:12 の「出版年」が API に含まれていません
```

行番号が特定できない場合はセクション名を書く。

### 2. 修正方針を1行で添える

```
悪い: [不足] 出版年が API に含まれていません
良い: [不足] 出版年が API に含まれていません
     -> data-model.md に books.published_year を追加し、API に載せる
```

**何が問題か** だけでなく **どうすればよいか** を書く。

### 3. 関連するファイルを併記する

不整合は2つ以上のファイルにまたがる。両方を示す。

```
[不足] SCR-001 の「出版年」が GET /books のレスポンスに含まれていません
   screens.md:12 (表示項目として定義) / api.md:34 (レスポンス定義)
```

### 4. 件数を種別ごとに集計する

```
検出した問題: 5件
  重大 2件 (不足1 / 出所不明1)
  軽微 2件 (過剰1 / マーカー欠落1)
  情報 1件 (用語のブレ1)
```

### 5. 0件のときは明示的に書く

```
検証結果: 問題は検出されませんでした

検証した項目:
  機能内の整合性  6項目 x 2機能 = 12件  全て OK
  機能間の整合性  5項目              全て OK
  形式の検証      5項目              全て OK

実装に進める状態です。
```

**「なし」を空欄にしない。** 検証したことが伝わらない。

## 完全な出力例

```
検証結果: 5件の問題を検出しました
対象: 機能2件 (book-lending, inventory) / ドキュメント11件

検出した問題: 5件
  重大 2件 (不足1 / 出所不明1)
  軽微 2件 (過剰1 / マーカー欠落1)
  情報 1件 (用語のブレ1)

重大 (実装が止まる)

  1. [不足] SCR-001 の「出版年」が GET /books のレスポンスに含まれていません
     features/book-lending/screens.md:12 / features/book-lending/api.md:34
     -> data-model.md に books.published_year を追加し、API に載せる

  2. [出所不明] items[].borrower_name の出所となるテーブルがありません
     features/book-lending/api.md:41
     -> data-model.md に employees テーブルが存在しません。追加が必要です

軽微 (設計の質)

  3. [過剰] books.isbn がどの画面でも使われていません
     features/book-lending/data-model.md:18
     -> カラムを削除するか、用途を screens.md に追記する

  4. [マーカー] REQ-012 に信頼性マーカーがありません
     features/inventory/requirements.md:45
     -> [確実] / [推測] / [要確認] のいずれかを付ける

情報 (判断が必要)

  5. [用語] 「社員」と「ユーザー」が混在しています
     features/book-lending/requirements.md:8 (社員)
     features/inventory/screens.md:15 (ユーザー)
     -> glossary.md でどちらかに統一する。別概念なら定義の違いを明記する

重大が2件あるため、実装に進める状態ではありません。

修正後、再度 /mitorizu:validate を実行して0件になることを確認してください。
```

## 検証したことを明示する

問題が0件でも、**何を検証したか** を示す。
検証範囲が伝わらないと、通ったことが過剰な安心につながる。

以下は**検証していない**ことも明記する。

```
このスキルが検証していないこと:
  - 要件の妥当性 (この要件が本当に必要かは人間の判断)
  - 設計の良し悪し (正規化の程度、命名の適切さは文脈依存)
  - 実装との一致 (コードは読んでいません)
  - 性能 (インデックスの十分性などは実測が必要)
```
