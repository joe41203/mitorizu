# EARS 記法の実例集

EARS (Easy Approach to Requirements Syntax) は、要件を曖昧さなく書くための構文。
そのままテストケースに落ちる形になる。

## 5つのパターン

### 1. Ubiquitous (常時)

常に成り立つ性質。トリガーも条件もない。

```
システムは全ての通信を TLS 1.2 以上で暗号化すること。
システムはパスワードを bcrypt でハッシュ化して保存すること。
```

**使いどころ**: セキュリティ要件、データ形式の制約、常に守るべき不変条件。

**注意**: 「常に」と言えるものだけに使う。条件付きなら別パターンへ。

### 2. Event-driven (イベント起点)

`〜したとき、システムは〜すること`

```
利用者がログインボタンを押したとき、システムはメールアドレスとパスワードを
検証し、成功時はダッシュボードへ遷移すること。

注文が確定したとき、システムは在庫を引き当て、確認メールを送信すること。

管理者がユーザーを無効化したとき、システムは当該ユーザーの
セッションを全て破棄すること。
```

**使いどころ**: 最も多く使うパターン。ユーザー操作、外部イベント、時刻起動。

**注意**: トリガーは1つに絞る。「AまたはBしたとき」は2要件に分割する。

### 3. State-driven (状態継続)

`〜の間、システムは〜すること`

```
注文が処理中の間、システムは同一注文に対する重複送信を拒否すること。

メンテナンスモードの間、システムは全ての書き込み API に対して
503 を返すこと。

利用者が未認証の間、システムは公開ページのみを表示すること。
```

**使いどころ**: 状態によって振る舞いが変わる場合。排他制御、モード切替。

**注意**: 「間」の開始と終了が明確であること。曖昧なら状態遷移図を先に描く。

### 4. Unwanted behaviour (異常系)

`もし〜した場合、システムは〜すること`

```
もしパスワードが5回連続で誤っていた場合、システムは当該アカウントを
15分間ロックし、ロック解除時刻を画面に表示すること。

もし決済ゲートウェイが30秒以内に応答しない場合、システムは注文を
保留状態にし、利用者に再試行を促すメッセージを表示すること。

もしアップロードされたファイルが10MBを超える場合、システムは
アップロードを拒否し、上限サイズを明示したエラーを返すこと。
```

**使いどころ**: エラー処理、例外、バリデーション違反、外部システム障害。

**注意**: **異常系こそ具体的な数値を書く**。「適切にエラーを返す」は要件ではない。

### 5. Optional feature (条件付き機能)

`〜の場合、システムは〜すること`

```
多要素認証が有効な場合、システムはパスワード検証成功後に
認証コードの入力を要求すること。

組織プランが Enterprise の場合、システムは監査ログを
90日間保持すること。
```

**使いどころ**: 機能フラグ、プラン別の挙動、オプション設定。

**注意**: 条件が3つ以上に分岐するなら表にする。要件文を増やしすぎない。

### 6. Complex (複合)

上記の組み合わせ。

```
多要素認証が有効な場合、利用者がパスワード検証に成功したとき、
システムは認証コードを登録済みの手段へ送信すること。

メンテナンスモードの間、もし管理者がログインを試みた場合、
システムは管理画面へのアクセスのみを許可すること。
```

**注意**: 3つ以上の条件を1文に詰め込まない。読めなくなる。

## 書き換えの実例

要件になっていない文を EARS に直す。

| 悪い例 | 問題 | EARS に直す |
| --- | --- | --- |
| ユーザーは注文をキャンセルできる | 主語がユーザー。システムの振る舞いでない | 利用者がキャンセルボタンを押したとき、システムは注文を取消状態に変更し、在庫を戻すこと |
| エラーを適切に処理する | 「適切に」が検証不能 | もし在庫引当に失敗した場合、システムは注文を作成せず、在庫不足の旨をエラーコード `OUT_OF_STOCK` で返すこと |
| パフォーマンスを考慮する | 要件でなく願望 | システムは一覧取得 API を 95 パーセンタイルで 500ms 以内に応答すること |
| 検索機能を実装する | 振る舞いが不明 | 利用者が検索語を入力して実行したとき、システムは商品名と説明文の部分一致で検索し、関連度順に20件ずつ返すこと |
| 必要に応じて通知する | 条件が不明 | 注文が発送済に変更されたとき、システムは購入者へ発送通知メールを送信すること |
| データを保存する | 何を、どこに、いつが不明 | 利用者が下書き保存を実行したとき、システムは入力内容を下書き状態で永続化し、保存時刻を表示すること |

## よくある失敗

### 1. 複数の振る舞いを1要件に詰める

```
悪い: 注文が確定したとき、システムは在庫を引き当て、決済を実行し、
      メールを送信し、管理者に通知すること。
```

4つの振る舞いがあり、どれか1つが失敗したときの挙動が書けない。

```
良い: REQ-010: 注文が確定したとき、システムは在庫を引き当てること。
      REQ-011: 在庫引当が成功したとき、システムは決済を実行すること。
      REQ-012: 決済が成功したとき、システムは購入者へ確認メールを送信すること。
      REQ-013: もし在庫引当に失敗した場合、システムは注文を作成せず
              エラーコード OUT_OF_STOCK を返すこと。
```

### 2. 実装方法を書いてしまう

```
悪い: システムは Redis にセッションを保存すること。
```

これは設計の決定であり要件ではない。要件は「何を満たすか」で、
「どう実現するか」は設計フェーズ (ADR) に書く。

```
良い: システムは複数サーバー構成でもセッションを共有できること。
     (実現方法は ADR-003 で Redis を選定)
```

ただし、外部制約として技術が決まっている場合は前提条件として書いてよい。

### 3. 数値を書かない

```
悪い: システムは大量のリクエストに耐えること。
良い: システムは秒間 1000 リクエストを 99 パーセンタイル 1 秒以内で処理すること。
```

数値がない要件は検証できない。分からない場合は `[要確認]` を付けて仮置きする。

### 4. 否定形だけで書く

```
悪い: システムは未認証ユーザーにデータを見せないこと。
良い: 利用者が未認証の間、システムは保護されたリソースへのアクセスに対して
     401 を返し、ログイン画面へ誘導すること。
```

「しないこと」だけでは、代わりに何が起きるか分からない。

## 要件IDの付け方

- `REQ-NNN` の通し番号。機能ごとにリセットしない (プロジェクト全体で一意)
- 一度振った番号は**欠番にしても再利用しない**。トレーサビリティが壊れる
- 削除した要件は `REQ-007: (削除) 理由` として残す

## テストケースへの変換

EARS で書かれた要件は、そのまま受入基準になる。

```
REQ-002: もしパスワードが5回連続で誤っていた場合、システムは当該アカウントを
        15分間ロックし、ロック解除時刻を画面に表示すること。

AC-002:
  前提: 有効なアカウントが存在する
  操作: 誤ったパスワードで5回ログインを試行する
  期待結果:
    - 5回目の応答でアカウントロックのエラーが返る
    - ロック解除時刻 (試行時刻+15分) が画面に表示される
    - 正しいパスワードでも15分間はログインできない
    - 15分経過後はログインできる
```

条件・トリガー・振る舞いが揃っているため、機械的に変換できる。
これが EARS を使う最大の理由。
