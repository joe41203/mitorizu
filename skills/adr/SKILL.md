# アーキテクチャ決定記録 (ADR)

**後から変えるのが高コストな決定** を、理由とともに残す。

半年後に「なぜこうなっているのか」を問われたとき、
記録が無いと**再検討のコストが最初の検討と同じだけかかる**。

**共通規約 `${CLAUDE_PLUGIN_ROOT}/references/conventions.md` を必ず先に読むこと。**

## 開始前に必ず読むもの

```bash
cat docs/mitorizu/.feedback/overrides.md 2>/dev/null
ls docs/mitorizu/adr/ 2>/dev/null
```

既存の ADR があれば読む。**矛盾する決定を書かないため。**

## 成果物

```
docs/mitorizu/adr/
  ADR-001-use-postgresql.md
  ADR-002-logical-deletion.md
```

ファイル名は `ADR-NNN-<英語の短い説明>.md`。**番号は再利用しない。**

## 何を ADR にするか

**全ての決定を ADR にしない。** 記録する価値があるものだけ。

### ADR にすべきもの

| 基準 | 例 |
| --- | --- |
| **後から変えるのが高コスト** | DB の種類、論理削除の方式、マルチテナント構成 |
| **他の選択肢が妥当だった** | REST か GraphQL か、モノリスかマイクロサービスか |
| **理由が自明でない** | なぜこのライブラリを避けたか |
| **将来見直す可能性がある** | 「今は不要だが規模が10倍になったら再検討」 |

### ADR にしないもの

| 基準 | 例 |
| --- | --- |
| 自明な選択 | HTTPS を使う、パスワードをハッシュ化する |
| 後から容易に変えられる | ボタンの色、ページネーションの件数 |
| 単なる作業記録 | 「〜を実装した」 |
| 個別の要件 | それは `requirements.md` に書く |

**迷ったら書く。** 書きすぎて困ることは少ないが、
書かなかった決定は後から復元できない。

## よく ADR になる決定

mitorizu の各スキルが扱う判断のうち、記録すべきもの。

| 決定 | どのスキルで出るか | なぜ高コストか |
| --- | --- | --- |
| DB の種類 | data-model / infra-diagram | 移行が困難 |
| 論理削除か物理削除か | data-model | 全クエリに影響。過去データが戻らない |
| マルチテナントの方式 | data-model | 全テーブルに影響 |
| ID の型 (連番 / UUID) | data-model | 全テーブルと API に影響 |
| 認証方式 | requirements / non-functional | 利用者の再登録が必要になる |
| API スタイル (REST / GraphQL) | api-design | クライアントの作り直し |
| リージョン | infra-diagram | データ移行が必要 |
| VPC の CIDR | infra-diagram | 作り直しが必要 |
| 監査ログの要否 | non-functional | 後付けは過去分が残らない |
| 個人情報の保持方針 | non-functional | 法的要件。移行が困難 |

## 進め方

### Phase 1: 記録する決定を特定する

以下から拾う。

```bash
cat docs/mitorizu/decisions.md 2>/dev/null
grep -rn "後から変更が高コスト\|ADR に記録" docs/mitorizu/ 2>/dev/null
```

各スキルが「ADR に記録するよう案内する」と書いている箇所に対応する。

複数ある場合、**1つずつ別の ADR にする。** まとめない。
後から個別に見直せなくなる。

### Phase 2: 検討した代替案を洗い出す

**採用しなかった案こそ重要。** これが無い ADR は価値が半減する。

```markdown
## 検討した選択肢

### 選択肢A: PostgreSQL (採用)
- 利点: JSON 型が使える。全文検索が組み込み
- 欠点: 運用の知識が必要

### 選択肢B: MySQL
- 利点: 情報が多い。運用経験がある
- 欠点: JSON の扱いが弱い

### 選択肢C: SQLite
- 利点: 運用が不要
- 欠点: 同時書き込みに弱い。将来スケールできない
```

**「他に選択肢が無かった」場合もそう書く。** それも情報。

### Phase 3: 決定の理由を書く

**「なぜ選んだか」より「なぜ他を選ばなかったか」を書く。**
前者は自明なことが多いが、後者は忘れられる。

```markdown
## 決定

PostgreSQL を採用する。

### 理由

- 蔵書のメタデータを JSON で持つ想定があり、JSON 型のサポートが必要 (REQ-005)
- 将来の全文検索を見据えて、組み込みの検索機能があるものを選ぶ

### MySQL を選ばなかった理由

運用経験はあるが、JSON の扱いが PostgreSQL より弱い。
今回は JSON の利用が確定しているため、経験より機能を優先した。

### SQLite を選ばなかった理由

運用不要は魅力だが、同時書き込みに弱い。
利用者50人・同時10接続 (NFR-005) を満たせない可能性がある。
```

### Phase 4: 結果と影響を書く

**この決定によって何が決まり、何が制約されるか。**

```markdown
## 結果

### この決定により決まること

- マイグレーションは Rails の PostgreSQL アダプタを使う
- 全文検索は pg_trgm または tsvector を使う
- インフラは RDS for PostgreSQL を選択する (ADR-005)

### この決定により制約されること

- SQLite での開発環境は使えない (Docker で PostgreSQL を立てる)
- MySQL 固有の機能は使えない

### 見直す条件

- 全文検索の性能が不足した場合、Elasticsearch の併用を検討する
- ただし DB の移行は行わない (コストが見合わない)
```

### Phase 5: 状態を設定する

ADR には状態がある。

| 状態 | 意味 |
| --- | --- |
| `提案中` | 検討中。まだ決定していない |
| `承認済` | 決定した。現在有効 |
| `非推奨` | 新規には使わないが、既存はそのまま |
| `置き換え済` | 別の ADR に置き換えられた (置き換え先を明記) |

**既存の ADR を書き換えない。** 決定が変わったら**新しい ADR を作り**、
古いものの状態を `置き換え済` にする。

```markdown
状態: 置き換え済 (ADR-012 により置き換え)
```

履歴が残ることに価値がある。上書きすると「なぜ変えたか」が失われる。

### Phase 6: 記録と次のステップ

1. `docs/mitorizu/adr/ADR-NNN-<説明>.md` を作る
2. `docs/mitorizu/README.md` の「4. データモデル」または該当節から ADR へリンクする
3. `docs/mitorizu/decisions.md` の該当項目に ADR 番号を添える

```
ADR を記録しました。

  docs/mitorizu/adr/ADR-001-use-postgresql.md
  docs/mitorizu/adr/ADR-002-logical-deletion.md

決定が変わった場合、既存の ADR は書き換えず、
新しい ADR を作って古いものを「置き換え済」にしてください。
```

### 終了前: 学んだことを記録する

利用者から訂正を受けたら、次回も同じ判断をすべきものだけを
`docs/mitorizu/.feedback/overrides.md` に追記する。**確認してから書く。**

## 書き方の原則

### 1. 決定した時点で書く

**後からまとめて書かない。** 理由を忘れる。
検討中の議論が新鮮なうちに記録する。

### 2. 未来の読み手を想定する

半年後の自分、または新しくプロジェクトに入る人が読む。
**前提知識を仮定しない。**

```
悪い: 前回の議論の通り PostgreSQL を採用
良い: 蔵書のメタデータを JSON で持つ要件 (REQ-005) があるため PostgreSQL を採用
```

### 3. 短く書く

**1 ADR は1画面に収まる長さ。** 長いと読まれない。
詳細な検討は別ドキュメントに分け、ADR からリンクする。

### 4. 事実と判断を分ける

```
事実: PostgreSQL は JSON 型をサポートしている
判断: 今回の要件では JSON が必要なため、これを重視した
```

### 5. 「決めなかった」ことも記録する

**先送りも決定。** なぜ今決めないかを書く。

```markdown
# ADR-008: マイクロサービス化は行わない

状態: 承認済

## 決定

MVP ではモノリスとする。マイクロサービス化は行わない。

## 理由

現時点で分割する境界が明確でない。
利用者50人・機能3つの規模では、分割のコストが利益を上回る。

## 見直す条件

- チームが3つ以上に分かれた場合
- デプロイの頻度が機能ごとに大きく異なるようになった場合
```
