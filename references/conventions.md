# mitorizu 共通規約

全スキルが従う共通ルール。各 SKILL.md から参照される。

## 0. パス変数について

SKILL.md 内の `${CLAUDE_PLUGIN_ROOT}` と `${CLAUDE_SKILL_DIR}` は、
Claude Code がプラグインを読み込むときに解決するパスを指す。

| 変数 | 指す場所 | 用途 |
| --- | --- | --- |
| `${CLAUDE_PLUGIN_ROOT}` | プラグインのルート | 共通の `references/` と `scripts/` |
| `${CLAUDE_SKILL_DIR}` | 各スキルのディレクトリ | そのスキル固有の `references/` と `scripts/` |

**成果物の出力先は常に「利用者のプロジェクトの cwd からの相対パス」** で、
`docs/mitorizu/...` に書く。プラグイン側には何も書き込まない。

変数が解決できない環境でこのファイルを直接読んでいる場合は、
プラグインの実体は `~/.claude/plugins/cache/` 配下、
または `--plugin-dir` で指定されたディレクトリにある。

## 1. 信頼性マーカー

生成する要件・設計の全項目に、根拠の強さを示すマーカーを付ける。
AI が「原典に基づく事実」と「補完した推測」を混ぜて出力する問題への対策。

| マーカー | 意味 | 人間の対応 |
| --- | --- | --- |
| `[確実]` | ユーザーの回答・既存コード・既存ドキュメントに明示的な根拠がある | 確認不要 |
| `[推測]` | 一般的な慣行や文脈からの合理的な補完。矛盾はないが原典にはない | 目視で流す |
| `[要確認]` | 判断材料が不足し、仮置きした。外れると後段の設計が崩れる | **必ず確認する** |

### 運用ルール

- マーカーは項目単位で付ける。文書単位でまとめない
- `[要確認]` は各フェーズ終了時に**一覧で再掲**する。埋もれさせない
- `[要確認]` が解決したら `[確実]` に昇格させ、スナップショットを更新する
- 迷ったら弱いほうに倒す。`[推測]` か `[要確認]` かで迷えば `[要確認]`

`[要確認]` が10件を超えたらヒアリング不足のサイン。次のラウンドで潰す。

## 2. EARS 記法

機能要件は EARS (Easy Approach to Requirements Syntax) で書く。
曖昧さを排し、そのままテストケースに落ちる形にするため。

| パターン | 構文 | 使う場面 |
| --- | --- | --- |
| Ubiquitous | システムは〜すること | 常に成り立つ性質 |
| Event-driven | **〜したとき**、システムは〜すること | イベント起点 |
| State-driven | **〜の間**、システムは〜すること | 状態が続く間 |
| Unwanted | **もし**〜した場合、システムは〜すること | エラー・例外 |
| Optional | **〜の場合**、システムは〜すること | 機能フラグ・オプション |
| Complex | 上記の組み合わせ | 条件が複合する場合 |

### 例

```
[確実] REQ-001: ユーザーがログインボタンを押したとき、システムはメールアドレスと
       パスワードを検証し、成功時はダッシュボードへ遷移すること。

[確実] REQ-002: もしパスワードが5回連続で誤っていた場合、システムは当該アカウントを
       15分間ロックし、ロック解除時刻を画面に表示すること。

[要確認] REQ-003: セッションが30分間無操作の間、システムは自動ログアウトすること。
       (30分は仮置き。業務要件により変わる)
```

### 書くときの注意

- 主語は「システム」に統一する。「ユーザーは〜できる」は要件ではなくユーザーストーリー
- 「〜など」「適切に」「必要に応じて」は禁止。検証できない
- 1要件1文。複数の振る舞いを含めない
- 要件IDは `REQ-NNN` 形式で通し番号

## 3. 出力先ディレクトリ

成果物は対象プロジェクトの `docs/mitorizu/` 配下に置く。

```
docs/mitorizu/
  README.md                   # 全成果物の目次と要約。ここが入口
  glossary.md                 # 用語集(ユビキタス言語)。全機能で共有
  entities.md                 # エンティティカタログ。全機能で共有
  decisions.md                # 確定事項スナップショット。全機能で共有
  adr/
    ADR-001-*.md              # アーキテクチャ決定記録
  features/
    <feature-slug>/
      requirements.md         # 要件定義書(EARS + マーカー)
      interview.md            # ヒアリング記録(質問と回答の履歴)
      screens.md              # 画面設計(表示項目定義)
      non-functional.md       # 非機能要件
      dataflow.md             # データフロー図(mermaid)
      data-model.md           # ER図 + テーブル定義 + DDL
      api.md                  # API設計の説明
      openapi.yaml            # OpenAPI 3.1
      traceability.md         # 画面 -> API -> テーブル の追跡表
  infra/
    <name>.d2                 # インフラ構成図ソース
    <name>.svg                # 生成物
```

`glossary.md` / `entities.md` / `decisions.md` の3つは**機能をまたいで共有**する。
新しい機能の要件を作るときは必ず既存の3ファイルを読み、矛盾・重複を検出する。

### ファイルが存在しない場合は新規作成する

`glossary.md` / `entities.md` / `decisions.md` / `README.md` について
「追記する」「更新する」と書かれている箇所は、
**ファイルが存在しなければ新規作成する**という意味を含む。

初回の機能設計では対象ファイルは必ず存在しない。
別スキルの実行を待たず、その場で作成してよい。

| ファイル | 不在時の動作 |
| --- | --- |
| `glossary.md` | 新規作成し、今回の用語を書く |
| `entities.md` | 新規作成し、今回のエンティティを書く |
| `decisions.md` | 新規作成し、今回の決定を書く |
| `README.md` | 新規作成する。テンプレートの見出し構造を作り、担当節のみ埋める |

`README.md` を新規作成する場合、
`${CLAUDE_PLUGIN_ROOT}/skills/docs-index/references/docs-readme-template.md`
の見出し構造をそのまま作り、**自分の担当節だけを埋める**。
他の節は見出しと「(未作成)」だけを置く。後続スキルが埋める。

全体を作り直したいときに `/mitorizu:docs-index` を使う。

### decisions.md は追記だけでなく失効も記録する

**判断が変わったときに追記だけすると、矛盾が同一ファイルに併存する。**

```
15行目 (features 期): 論理削除 (discarded_at) を使う
47行目 (data-model 期): discarded_at は置かない
```

これでは「路線を復元できる」という目的が損なわれる。

#### 失効させる手順

**過去の記述を削除しない。** 履歴に価値がある。
代わりに**失効の印を付け、新しい決定から参照する。**

```markdown
## 削除方式

~~[2026-08-14] 論理削除 (discarded_at) を使う~~
  **失効** (2026-08-15 の決定により置き換え)

[2026-08-15] 物理削除とし、取消は status で表現する
  変更の理由: 請求書は取消と削除の意味が異なるため、
              汎用の discarded_at では判定が二重化する
  置き換えたもの: 2026-08-14 の論理削除の決定
```

| 書くもの | 理由 |
| --- | --- |
| 取り消し線と「失効」 | 過去の決定が無効であることを示す |
| 失効させた日付 | いつ変わったか |
| **変更の理由** | なぜ変えたか。これが最も重要 |
| 置き換え関係 | どの決定がどれを置き換えたか |

#### 書き込む前に既存を読む

**追記する前に `decisions.md` 全体を読み、矛盾する記述が無いか確認する。**

```bash
cat docs/mitorizu/decisions.md 2>/dev/null
```

矛盾を見つけたら、**追記する前に失効処理をする。**
気づかずに追記すると、後から validate で検出されるだけになる。

後から変えるのが高コストな決定は、`decisions.md` ではなく
**ADR に記録する** (`/mitorizu:adr`)。ADR には状態管理の仕組みがある。

### フィードバックの蓄積と反映

**mitorizu はプロジェクトごとに学習する。**
利用者の訂正や検証で見つかった失敗を記録し、次回以降の既定を変える。

蓄積先は**プロジェクト内**。プラグイン本体は書き換えない
(`/plugin update` で消えるため、また他プロジェクトに影響するため)。

```
docs/mitorizu/.feedback/
  overrides.md      既定を上書きするルール (利用者の訂正から)
  learnings.md      繰り返し起きた失敗と対策 (validate の検出から)
```

#### 各スキルの開始時に読む

**成果物を書き始める前に `.feedback/` を読む。**
既定より優先度が高い。無ければ既定で進める。

```bash
cat docs/mitorizu/.feedback/overrides.md 2>/dev/null
cat docs/mitorizu/.feedback/learnings.md 2>/dev/null
```

#### 各スキルの終了時に記録する

以下に該当したら `overrides.md` に追記する。**利用者に確認を取ってから書く。**

| 拾うもの | 例 |
| --- | --- |
| 既定への訂正 | 「命名は camelCase にして」「テーブル名は単数形で」 |
| 質問への不満 | 「その質問は不要」「毎回聞かないで」 |
| 出力形式の指定 | 「DDL は不要」「マイグレーションは Prisma で」 |
| 判断基準の変更 | 「MVP でも論理削除を入れる」 |

```markdown
## 命名規約

[2026-08-14] テーブル名は単数形を使う
  理由: 既存システムが単数形で統一されているため
  適用: data-model スキル

## 出力

[2026-08-14] Rails マイグレーションは生成しない
  理由: Prisma を使っているため
  適用: data-model スキル
```

**記録するのは「次回も同じ判断をすべきこと」だけ。**
その場限りの指示 (「今回はこの機能名で」) は記録しない。

#### validate の検出から学ぶ

`/mitorizu:validate` が**同じ種別の指摘を3回以上**出したら、
それはスキルの既定が実態に合っていないサイン。`learnings.md` に記録する。

```markdown
## 繰り返し検出された問題

[2026-08-14] 用途の空欄が毎回20件以上検出される
  原因: 監査カラム (created_at 等) に用途を書いていなかった
  対策: 例外として認める旨を data-model 実行時に最初から適用する
  検出回数: 3回

[2026-08-14] 「社員」と「ユーザー」の混在
  原因: 要件定義とデータモデルで別の語を使っていた
  対策: glossary.md に「社員 = Employee」を登録済み。以後は統一
  検出回数: 4回
```

#### 記録の作法

- **日付を必ず付ける** (いつの判断か分かるように)
- **理由を書く** (なぜそうするかが分からないと、後で覆せない)
- **適用範囲を書く** (どのスキルに効くか)
- **古くなったものは削除する** (前提が変わったら残さない)

`.feedback/` が肥大化したら、利用者に整理を提案する。
50行を超えたら見直しの目安。

### 非対話で実行された場合

`AskUserQuestion` が使えない状況 (バッチ実行、他エージェントからの呼び出し、
CI など) では、**質問せずに以下の手順で進める**。作業を止めない。

1. **推奨案 (各選択肢の先頭に置いたもの) を採用する**
2. 採用した選択を `[推測]` または `[要確認]` でマークする
   - 一般的な慣行から妥当に決まるもの: `[推測]`
   - 業務要件次第で変わるもの (期限の日数、上限値、権限の粒度): `[要確認]`
3. **想定した質問と採用した回答を記録する**
   - 要件定義なら `interview.md` に「質問 / 採用した回答 / 根拠」を書く
   - それ以外は成果物の「要確認項目」節に書く
4. 完了時に「ユーザー確認が必要な項目」として一覧で提示する

**推奨案が明らかに不適切な場合は、推奨案に従わず妥当な案を選ぶ。**
その場合は理由を `[要確認]` に添えて記録する。

### README.md は全成果物の入口

`docs/mitorizu/README.md` は目次ではなく、**これ1枚読めば全体が分かる文書**にする。
各成果物へのリンクに加えて、要約を含める。

**各スキルは最終フェーズで README.md を更新する。**
自分が生成した成果物の要約を、該当する節に追記または更新する。

| スキル | 更新する節 |
| --- | --- |
| discovery | サービス概要 (課題と MVP のスコープ) |
| **features** | **機能一覧 (全機能の行を作る)、要確認項目** |
| requirements | 機能一覧、その機能の要件サマリ、用語集の更新 |
| **non-functional** | **非機能要件の節 (新設)** |
| **state-machine** | **その機能の節に状態遷移図を追加** |
| screens | その機能の画面一覧 |
| data-model | データモデル概要、エンティティ一覧 |
| api-design | エンドポイント一覧、検証結果 |
| infra-diagram | インフラ構成 |
| **tasks** | **機能一覧にタスク数と実装状況** |
| **adr** | **各節から該当する ADR へのリンク** |

**担当節が無いスキルは README を更新しない。**
ただし README が存在しない場合の新規作成は、どのスキルでも行ってよい
(見出し構造を作り、担当節のみ埋める)。

`features` は最初に全機能の行を作る役割を持つ。
以降のスキルはその行の列 (要件・画面・データ・API) を埋めていく。

README.md が存在しない場合は `/mitorizu:docs-index` で新規作成する。
存在する場合は該当節のみを更新し、他の節には触れない。

## 4. 読み手と用語の使い分け

**成果物によって読み手が違う。** 全てをエンジニア向けに書かない。

| 成果物 | 主な読み手 | 技術用語 |
| --- | --- | --- |
| `business-flow.md` | **業務担当者・発注者** | **使わない** |
| `requirements.md` | 業務担当者 + エンジニア | 最小限 |
| `screens.md` | 業務担当者 + エンジニア | 最小限 |
| `non-functional.md` | 業務担当者 + エンジニア | 一部使う (数値は必須) |
| `state-machine.md` | エンジニア中心 | 使う |
| `data-model.md` | エンジニア | 使う |
| `api.md` | エンジニア | 使う |
| `sequence.md` | エンジニア | 使う |
| `tasks.md` | エンジニア | 使う |

### 技術用語を使わない文書での書き換え

| 技術用語 | 業務担当者向けの表現 |
| --- | --- |
| エンティティ / テーブル | 情報の種類、〜の記録 |
| カラム / フィールド | 項目 |
| API / エンドポイント | (書かない。「システムが〜する」で表現) |
| レコード | 1件のデータ |
| バリデーション | 入力チェック |
| トランザクション | (書かない。「まとめて処理される」等) |
| 論理削除 / 物理削除 | 「記録を残して削除」「完全に削除」 |
| enum / 状態 | 状態、区分 |
| 認証 / 認可 | ログイン、権限 |
| N+1 / インデックス | (書かない。性能の話は非機能要件へ) |

### 両方の読み手がいる文書の書き方

`requirements.md` と `screens.md` は両方が読む。以下で対応する。

- **本文は業務の言葉で書く。** 「システムは注文を確定すること」
- **技術的な補足は括弧か脚注に逃がす。** 「(実装上は orders テーブルに記録)」
- **ID (REQ-NNN, SCR-NNN) は残す。** 参照に必要。番号自体は読み飛ばせる

**業務担当者が読めない要件定義書は、合意の役に立たない。**
要件定義は本来、発注者と合意するためのもの。

## 5. 対話の進め方

### 質問の粒度

- 既定は **3〜5問のまとまり**。一度に10問投げない
- 方針を左右する重い問い(アーキテクチャの分岐点など)は **1問だけ単独**で投げる
- 細部の詰め(必須項目かどうか等)は5問まとめてよい
- AskUserQuestion ツールを使う。選択肢には必ず推奨案を先頭に置き「(推奨)」と付ける

### 各ラウンドの構造

**冒頭に現在地を出す**:

```
[フェーズ 2/5: データモデル]
確定済み: 認証はメール+パスワード / 多言語対応なし / 想定10万ユーザー
未決: エンティティの粒度、履歴保持の要否
```

**末尾に解釈を書き戻す**:

回答を受けたら「つまりこう理解した」を1〜3行で明示する。
誤解があればその場で訂正させる。後段に伝播させない。

### フェーズ終了時

`docs/mitorizu/decisions.md` に確定事項を追記する。これが「路線」の実体になる。
セッションが切れても、このファイルから復元できる状態を保つ。

## 6. 既存資産の参照

要件を作る前に、対象プロジェクトの以下を必ず確認する。
質問が実態に即したものになり、既に決まっていることを聞かずに済む。

1. `docs/mitorizu/glossary.md` `entities.md` `decisions.md` — 既存の確定事項
2. `CLAUDE.md` — プロジェクト規約
3. `README.md` — プロジェクトの目的と構成
4. 既存のスキーマ定義 (migration, schema.rb, prisma/schema.prisma, *.sql など)
5. 既存の API 定義 (openapi.yaml, routes, controller など)
6. 既存のコード — 認証・権限まわりは特に確認する

見つかった事実は `[確実]` として扱う。ユーザーに聞き直さない。

## 7. 用語の統制

大規模サービスでは、同じ概念に別名がつくことが最大の負債になる
(User / Account / Member が混在するなど)。

### glossary.md は業務語と技術語の対応表

**用語集は「業務担当者の言葉」と「実装で使う名前」を橋渡しする表。**
片方だけでは、会話が噛み合わなくなる。

```markdown
| 業務での呼び方 | 実装での名前 | テーブル/カラム | 定義 | 使ってはいけない別名 |
| --- | --- | --- | --- | --- |
| 管理者 | `Admin` | `users.role = 'admin'` | 蔵書を登録・削除できる人 | 運営者、アドミン |
| 会社 | `Company` | `companies` | 契約単位の組織 | 企業、法人、テナント |
| 社員 | `Employee` | `employees` | 会社に所属し本を借りる人 | ユーザー、メンバー |
| 蔵書 | `Book` | `books` | 会社が所有する書籍 | 図書、書籍 |
| 貸出 | `Lending` | `lendings` | 社員が本を借りた記録 | レンタル、借用 |
```

**列の意味:**

| 列 | 誰が使うか | 書くこと |
| --- | --- | --- |
| 業務での呼び方 | 業務担当者 | 打ち合わせで実際に使われる日本語 |
| 実装での名前 | エンジニア | クラス名・モデル名 (パスカルケース) |
| テーブル/カラム | エンジニア | 実際の DB 上の名前 |
| 定義 | 両方 | 1行で。何を指すか |
| 使ってはいけない別名 | 両方 | 同じ意味で使われがちな他の語 |

#### 業務語を先に決める

**実装名から業務語を決めない。逆にする。**

```
悪い: Company というモデルを作ったので、業務でも「カンパニー」と呼ぶ
良い: 業務では「会社」と呼んでいるので、実装名を Company にする
```

業務担当者は自分たちの言葉を変えない。合わせるのは実装側。

#### 1つの業務語に複数の実装名を当てない

```
悪い: 「管理者」が Admin と Manager の2つのクラスになっている
良い: 「管理者」= Admin。「部門長」= Manager と、業務語も分ける
```

業務語が同じなのに実装が分かれているなら、**業務語の切り分けが足りない**。
逆に実装が同じで業務語が複数あるなら、**用語を統一する。**

### 用語を追加・照合する手順

- 新しい名詞が出たら `glossary.md` を確認し、既存の用語と衝突しないか検査する
- 類義語を見つけたら**その場でユーザーに確認**し、どちらに統一するか決める
- 決まった用語は `glossary.md` に追記する。上記5列を全て埋める
- **業務担当者との打ち合わせで出た言葉は、そのまま「業務での呼び方」に記録する**

### 禁止別名の照合 (全スキル共通)

**`glossary.md` に登録した「使ってはいけない別名」は、
成果物を書き終えたときに必ず照合する。** 登録するだけでは意味がない。

```bash
# glossary.md の禁止別名を抽出して、今書いた成果物に含まれていないか調べる
grep -oE '\|[^|]*\|[^|]*\|[^|]*\|\s*([^|]+)\s*\|' docs/mitorizu/glossary.md
```

自動抽出が難しい場合は、`glossary.md` を読んで禁止語を目視で拾い、
生成した成果物を1語ずつ検索する。

```bash
# 例: 禁止別名が「品目」の場合
grep -n '品目' docs/mitorizu/features/<slug>/*.md
```

見つかったら**その場で修正する。** 後回しにすると全ファイルに広がる。

上流のスキル (requirements) が登録した禁止語を、
下流のスキル (screens / data-model / api-design) が使ってしまうのが典型的な失敗。
**登録した本人以外がチェックする仕組みが無いと素通りする。**

## 8. 命名規約 (Rails way)

**既定は Rails の命名規約に従う。** 対象プロジェクトが Rails でなくても既定はこれ。

ただし**既存のスキーマが検出できた場合は、そちらの規約に合わせる**。
既存 `schema.rb` / `prisma/schema.prisma` / `migrations/` を読み、
そこで使われている規約を優先する。既存と新規で命名がぶれるほうが害が大きい。

### テーブル名

| 対象 | 規約 | 例 |
| --- | --- | --- |
| テーブル | 複数形・スネークケース | `users`, `order_items` |
| 結合テーブル (HABTM) | 両モデル名をアルファベット順 | `orders_products` |
| STI | 単一テーブルに `type` カラム | `vehicles` (+ `type`) |

### カラム名

| 用途 | 規約 | 例 |
| --- | --- | --- |
| 主キー | `id` (bigint, auto increment) | `id` |
| 外部キー | `<単数形>_id` | `user_id`, `order_id` |
| ポリモーフィック | `<name>_type` + `<name>_id` | `commentable_type`, `commentable_id` |
| 日時 | `_at` サフィックス | `created_at`, `published_at` |
| 日付のみ | `_on` サフィックス | `due_on`, `birth_on` |
| 真偽値 | 形容詞または過去分詞。`is_` を付けない | `published`, `active`, `archived` |
| カウンタキャッシュ | `<複数形>_count` | `comments_count` |
| 並び順 | `position` | `position` |
| 論理削除 | `discarded_at` (discard gem 準拠) | `discarded_at` |

真偽値に `is_` を付けないのは、Rails が `published?` という述語メソッドを
自動生成するため。`is_published` だと `is_published?` になり冗長になる。

### 必須カラム

- `id` — 主キー
- `created_at` / `updated_at` — 原則すべてのテーブルに置く

### 避けるべき名前

Rails の予約語・慣習と衝突するため使わない。

| 避ける | 理由 | 代替 |
| --- | --- | --- |
| `type` | STI で予約されている | `category`, `kind` |
| `class` | Ruby の予約語 | `classification` |
| `object`, `send`, `hash` | Object のメソッドと衝突 | 具体的な名前にする |
| `<単数形>_ids` | `has_many` が生成するメソッドと衝突 | 使わない |

### インデックスと制約

| 対象 | 規約 |
| --- | --- |
| インデックス名 | `index_<table>_on_<columns>` |
| 一意インデックス | `index_<table>_on_<columns>` + `unique: true` |
| 外部キー制約 | `fk_rails_<hash>` (Rails 自動生成) |

外部キーには**必ずインデックスを張る**。Rails は自動で張らない。

### Rails 以外のプロジェクトの場合

既存スキーマから規約を検出できず、かつユーザーが別の規約を指定した場合のみ、
そちらに従う。指定がなければ上記の Rails way を使う。

## 9. 図の使い分け

| 図 | ツール | 理由 |
| --- | --- | --- |
| データフロー図 | mermaid `flowchart` | 抽象度が高くアイコン不要 |
| ER図 | mermaid `erDiagram` | mermaid が最も得意 |
| シーケンス図 | mermaid `sequenceDiagram` | 同上 |
| 画面遷移図 | mermaid `stateDiagram-v2` | 同上 |
| **インフラ構成図** | **D2** | クラウドのアイコンとネストが必要 |

インフラ構成図だけ D2 を使う。mermaid にはベンダーのサービスアイコンがなく、
VPC -> AZ -> Subnet の入れ子も 3 段以上で破綻するため。詳細は `d2-guide.md` を参照。
